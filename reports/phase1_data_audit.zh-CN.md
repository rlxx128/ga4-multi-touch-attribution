# Phase 1 数据审计

最后更新：2026-08-04

## 状态与范围

Phase 1 审计执行在 Phase 2A 开始前已被接受。审计使用公开、混淆的 GA4 电商样本；发现不代表 Google Merchandise Store 的实际业务表现。下文保留 Phase 1 决策请求作为历史证据；已批准定义及剩余 Phase 2A 门决策记录在 `docs/decisions.zh-CN.md`。

审计完全只读。它没有创建 BigQuery 数据集或表，也未使用渠道映射、Session 模型、订单模型、归因模型、Markov 模型、Shapley 模型或仪表板。

## 查询安全与成本

- 来源：`bigquery-public-data.ga4_obfuscated_sample_ecommerce.events_*`。
- 固定来源范围：后缀 `20201101` 至 `20210131`。
- BigQuery 位置：`US`。
- 物理查询作业：12 个，包括两个宽流量来源扫描的按月分块。
- 12 个作业均在执行前立即通过 dry run。
- 每个作业使用 `maximum_bytes_billed = 1,000,000,000`。
- 最大 dry-run 估算：995,193,539 字节。
- 所有作业处理总字节数：4,577,686,286。
- 总计费字节数：4,583,325,696。
- 验证检查无失败：8 项无需审查即通过，23 项在记录审查事项后通过。

每个作业的精确估算、处理字节、计费字节、SQL 哈希和行数位于 `reports/tables/phase1_query_costs.csv`。

## 来源架构与日期覆盖

配置范围包含 92 个日分片。92 个均存在且非空，每行 `event_date` 都与表后缀一致。确认的来源日期范围为 2020-11-01 至 2021-01-31。

审计统计到 4,295,584 个事件和 270,154 个不同 `user_pseudo_id` 值。每个选定分片都包含所有必需的事件、电商、标识符和首次用户流量来源字段。

历史样本包含：

- 带字符串和整数值的 `event_params`；
- `ecommerce.transaction_id`；
- `ecommerce.purchase_revenue`；
- `ecommerce.purchase_revenue_in_usd`；
- `traffic_source.source`、`traffic_source.medium` 和 `traffic_source.name`。

它不包含 `collected_traffic_source` 或 `session_traffic_source_last_click`，因此无法直接使用本样本中较新的已收集流量或 Session 末次点击导出。

## 事件分布

审计观察到 17 个事件名称，没有空值或空白名称。计划分析所需的主要漏斗事件均存在：

| 事件 | 事件数 | 不同用户数 |
|---|---:|---:|
| `session_start` | 354,970 | 267,116 |
| `view_item` | 386,068 | 61,252 |
| `add_to_cart` | 58,543 | 12,545 |
| `begin_checkout` | 38,757 | 9,715 |
| `add_shipping_info` | 19,722 | 9,714 |
| `add_payment_info` | 13,899 | 5,751 |
| `purchase` | 5,692 | 4,419 |

未观察到 `refund` 事件。由于 Session 和订单定义尚未批准，本审计不把事件数解释为漏斗转化率。

## 用户与候选 Session 标识符

全部 4,295,584 个事件、354,970 个 `session_start` 事件和 5,692 个购买事件都具有 `user_pseudo_id` 和整数 `ga_session_id`。未观察到重复 `ga_session_id` 参数、非整数或非正数值。

原始 `ga_session_id` 并非全局唯一：9,906 个 Session ID 值关联多个用户。所有事件中有 349,545 个原始 Session ID，但 `user_pseudo_id` 加 `ga_session_id` 候选键有 360,129 个。这支持但不自行批准所提议的复合 Session 键。

## 购买事件与交易质量

`purchase` 事件仅作为审计总体。尚未实施最终转化或订单定义。

| 诊断 | 观察值 |
|---|---:|
| 购买事件 | 5,692 |
| 购买用户 | 4,419 |
| 交易 ID 为空的事件 | 23 |
| 交易 ID 空白的事件 | 0 |
| 交易 ID 为 `(not set)` 的事件 | 883 |
| 与 `(not set)` 关联的用户 | 767 |
| 包含 `(not set)` 的候选用户—交易键 | 5,233 |
| 排除空值和 `(not set)` 后的候选用户—交易键 | 4,466 |
| 购买事件重复的有效候选键 | 314 |
| 这些重复有效键的额外事件 | 320 |
| 收入冲突的有效重复键 | 0 |

有 16 个交易 ID 值关联多个用户。其中一个是 `(not set)` 占位符，其他 15 个表明交易 ID 单独使用并不是该样本的安全订单键。将 `user_pseudo_id` 与可用交易 ID 组合可避免跨用户冲突。

314 个重复有效候选键包含 634 个购买事件；每个键内有限收入一致。因此使用每个键观察到的最大收入不会改变这些重复组的收入，并可防止重复事件使收入倍增。订单时间戳规则仍待决定，建议使用最早购买时间戳。

## 收入质量

事件层面有 450 个购买事件的 `ecommerce.purchase_revenue` 为空。每个购买事件都有 `ecommerce.purchase_revenue_in_usd`，但相同 450 个事件的美元值非正。在排除空值和 `(not set)` 交易 ID 并按候选用户—交易键分组后，全部 4,466 个候选订单的最大美元收入均为正。

该审计总体中：

- 原始有限本地购买收入：362,165；
- 原始有限美元购买收入：362,165；
- 含 `(not set)` 候选键的最大收入：335,986；
- 排除 `(not set)` 后候选键的最大收入：308,830。

本地与美元总额在审计候选规则下相符。建议使用美元字段以明确统一币种，但所有者须在 Phase 2 前批准收入字段和排除/去重规则。

## 流量来源可用性

样本没有现代 collected 或 session-last-click 结构。首次用户流量字段在每个事件上都有值，但描述的是获客，不能当作每个后续 Session 的来源。

所有事件中：

| 候选字段 | 非空白覆盖 | 占所有事件的占位符比例 |
|---|---:|---:|
| 事件参数来源 | 33.25% | 4.77% |
| 事件参数媒介 | 33.50% | 2.76% |
| 事件参数广告系列 | 33.50% | 3.38% |
| 事件参数页面引荐 | 26.25% | 0.00% |
| 首次用户来源 | 100.00% | 33.52% |
| 首次用户媒介 | 100.00% | 21.22% |
| 首次用户广告系列 | 100.00% | 25.34% |

`session_start` 事件上的来源、媒介及广告系列事件参数没有可用值；页面引荐在 4.57% 的 `session_start` 事件上非空白。首次用户字段完全填充，但含大量 `<Other>`、`(not set)`、`(data deleted)` 或 `unknown` 占位符。

按频率排序的值表明，事件级来源以内部或自引荐值为主，尤其是 `shop.googlemerchandisestore.com`。常见媒介包括 `referral`、`organic`、`(none)`、`<Other>`、`(data deleted)`、`cpc`、`affiliate` 和 `email`。最常见的引荐也来自内部店铺页面。因此，引荐推断需要明确的自引荐排除规则，不能未经审查就作为通用回退。

所有硬性 Phase 1 验收检查通过：

- 所有选定分片都有必需架构字段；
- 全部 92 个预期日期通过后缀/日期验证；
- 事件名称非空且购买事件存在；
- 用户及候选 Session 标识符已量化并核对；
- 购买、交易、重复和收入问题已量化；
- 已生成流量来源字段、空值率、占位符及样本值；
- 所有作业均只读且在固定单查询上限内。

审计已完成，但必须批准下列即时决策后才能开始 Phase 2。

## Phase 2 前的决策请求

### 1. 转化、订单身份与排除

- 方案 A：使用 `purchase`；按 `user_pseudo_id` 加非空、非空白、非占位符交易 ID 建立订单键；排除 23 个空 ID 事件和 883 个 `(not set)` 事件。
- 方案 B：在另行批准的替代订单规则下保留占位符或空 ID 购买事件。
- 建议：方案 A。它明确、可复现，并避免将 767 位用户合并到同一个 `(not set)` 标识符下。

### 2. 重复购买处理

- 方案 A：保留最早购买时间戳，使用每个批准订单键观察到的最大收入，并报告重复数。
- 方案 B：使用其他时间戳或收入聚合。
- 建议：方案 A。314 个重复有效键的收入一致，该规则可防止 320 个重复有效事件使收入倍增。

### 3. 用户与 Session 键

- 方案 A：用户使用 `user_pseudo_id`，Session 键使用 `user_pseudo_id` 加 `ga_session_id`。
- 方案 B：批准其他用户或 Session 身份。
- 建议：方案 A。两个字段均完整，且 9,906 个原始 Session ID 在用户间冲突。

### 4. 收入字段

- 方案 A：`ecommerce.purchase_revenue_in_usd`。
- 方案 B：`ecommerce.purchase_revenue`。
- 建议：方案 A，以明确统一币种报告。应用建议的排除和去重后，两个字段产生相同的审计合格总额。

### 5. Session 流量来源优先级

- 方案 A：在每个批准候选 Session 内，依次使用最早可用事件参数来源/媒介/广告系列、批准自引荐规则下的外部引荐、明确标注的首次用户流量来源回退，最后为 Direct 或 Unknown。
- 方案 B：每个 Session 都使用首次用户流量来源。
- 方案 C：不使用首次用户回退，把缺少支持的 Session 视为 Direct 或 Unknown。
- 建议：方案 A，并要求 Phase 2 按回退层级报告覆盖。方案 B 会错误地把获客字段描述为 Session 来源。方案 C 较保守，但可能把过多 Session 归为 Direct/Unknown。

### 6. 渠道映射

渠道映射仍待决定。只有批准流量来源优先级后，才能使用已观察值表起草互斥有序规则。本阶段未实施任何映射规则。
